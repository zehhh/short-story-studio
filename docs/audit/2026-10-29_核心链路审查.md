## 高危

### H1 整稿扩写兜底把 `int` 和 `str` 比较，必抛 TypeError

- **位置**：`studio/pipeline.py:3165`
- **代码**：

```python
3162:                new_full = writer.chat(sys_p, user_p).strip()
3163:                new_w = count_words_zh(new_full)          # int
3164:                n_heads = sum(1 for ln in new_full.splitlines() if _SEC_HEAD.match(ln.strip()))
3165:                if new_w >= full and n_heads >= 3:        # full 是 str
3166:                    full = new_full
3167:                    total = new_w
```

- **问题**：`new_w` 是 `count_words_zh()` 返回的 `int`，`full` 是整稿字符串。Python 3 下 `int >= str` 直接 `TypeError: '>=' not supported between instances of 'int' and 'str'`。
  触发链路清晰：`word_gate` 主循环（`pipeline.py:3083` `while (total < gate_floor or total > ceil) and rounds < max_r:`）→ 3124 `if total < gate_floor:` → 3129-3142 逐节扩写但 `gain` 累计不足 400 → **3148 `if total < gate_floor and gain < 400 and rounds == max_r - 1:`** 进入整稿扩写兜底 → 3165 抛异常。
  逃逸路径完整：`word_gate`（2995-3229）**全函数没有 try**，三个调用点 `pipeline.py:3604`、`4145`、`4160` 也都没有 try（3604 在 `stage_polish` 顶层，直接暴露给 CLI）。后果：**调了 LLM、写了 8000 字稿，最后一步崩掉，整轮产出不落盘**。
  对照 `pipeline.py:3113` 同函数内的正确写法 `if new_w >= total * 1.1 and n_heads >= 3:` —— 这行用 `total`（int），可以确认 3165 是笔误而非设计。
  把 `full` 换成 `total` 之外，还有一个**逻辑遗漏**：这里想判断的是"扩写后确实变长了"，但 `full` 在 3151 被重新赋值过，即便语法正确也拿不到"原稿长度"。
- **修法**：

```python
_old_w = count_words_zh(full)          # 3151 之后、3162 之前取基准
...
if new_w >= _old_w * 1.05 and n_heads >= 3:
```

并给 `word_gate` 内部这段整稿改写加一层 `try/except Exception` 兜底（与 4255、4277 的"失败留痕不毁稿"策略一致），崩溃时 `print` + 保留原稿 + 记 `runlog.event(..., level="error")`。
- **确定性**：代码路径明确可达；是否已在生产触发取决于是否出现过"最后一轮单节扩写增益 < 400"（这类稿子常见）。**需实测**：构造 `total=6000 / floor=8000 / max_r=3` 的稿子跑一次 `stage_polish` 即可复现。

### H3 `todo` 用"文件存在"判定完成，半状态章被永久跳过

- **位置**：`studio/pipeline.py:2324`（配合 `studio/drafts.py:161`）
- **代码**：

```python
2324:    todo = [c["no"] for c in chs if not project.chapter_file(c["no"]).exists()]
...
2327:    if not todo:
2328:        print("[stage] 各章均已扩写，跳过")
2329:        return
```

- **问题**：`drafts.py` 明确设计了一套"提交凭据"——`commit_chapter()` 先原子写正文、再原子写 `chNN.commit.json`，`is_committed()` 用 `sha256` 校验两者一致才认为"这一章真的完成了"（`drafts.py:161-176` 的 docstring 原话是"半状态……一律不算——这正是要暴露的问题"）。但 `stage_write` 的入口判据是 `.exists()`，**完全不看 commit 标记**。
  于是：第 3 章在 `pipeline.py:2463 _drafts.commit_chapter(...)` 的正文写入与标记写入之间崩溃（或 `_save_draft` 已把草稿提升、正文被写了一半），下次 `run` / `continue` 时第 3 章不在 `todo` 里，**永远不会被重写**；而 `reviews/ch03.json` 可能压根没写（2462 在 2463 之前，只能保证"评审先于提交"）。管线带着一个未过门禁的章节一路跑到成稿，`list_recoverable()` 虽然能扫出来（`drafts.py:183`），但没有任何代码把它接回 `todo`。
- **修法**：把完成判据换成提交凭据，并对旧项目做兼容：

```python
    todo = [c["no"] for c in chs
            if not project.chapter_file(c["no"]).exists()
            or not _drafts.is_committed(project, c["no"])]
```

同时给"存在但不 is_committed"的章打一行醒目日志（`[stage] ⚠ 第NN章为半状态（有正文无提交标记），重写`），否则用户会看到一章被莫名重写却不知道为什么。

### H4 读者团 LLM 失败时伪造 7.2 分，直接把评分门判成"不过"

- **位置**：`studio/agents.py:213-217`（`ReaderPanel.score`）
- **代码**：

```python
212:            try:
213:                r = self.llm.chat_json(system, user)
214:            except Exception:  # noqa: BLE001
215:                r = {"persona": p["name"], "score": 7.2, "feel": "（读机临时故障，按中下分保守计）", "advice": ""}
216:            r.setdefault("persona", p["name"])
217:            r["score"] = float(r.get("score", 7.0))
```

- **问题**：这是典型的"吞异常导致功能静默失效"。7.2 分被写进正常的 `scores` 列表，随后：

```python
agents.py:765:        avg = statistics.mean(s["score"] for s in scores)
agents.py:767:        while avg < threshold and rnd < max_reader:      # threshold 默认 7.5（agents.py:683）
```

`7.2 < 7.5` → **无论稿子好坏都判"读者团不过"**，触发一次完整的 `writer.rewrite()` 整章重写（`agents.py:772`）。三种坏法：
1. 单次网络抖动 → 一次白烧的整章重写；
2. 读者团全部故障 → `avg` 恒等于 7.2，循环跑到 `max_reader`（默认 2）用尽，`report["gate"] = "maxed_reader"`（`agents.py:781-783`），**一篇本来合格的稿子被记成"读者团打满"**；
3. `report["reader_scores"]` / `reader_avg` 里全是伪造分，复盘/看板读到的是假数据，且 `report` 里**没有任何 degraded 标记**可区分。

对比同文件的正确做法：`_gate_review_reader` 遇到主编返回 `degraded` 会 `report["review_error"]` + `report["gate"] = "degraded_review"`；情绪门同理有 `degraded_emotion`。读者团是唯一没有降级通道的一环。
- **修法**：

```python
            try:
                r = self.llm.chat_json(system, user)
            except Exception as e:
                # 不伪造分数：标记降级，交给上层决定是否计入
                out.append({"persona": p["name"], "score": None,
                            "degraded": True, "error": f"{type(e).__name__}: {e}"})
                continue
            r.setdefault("persona", p["name"])
            r["score"] = float(r.get("score", 7.0))
```

调用侧（`agents.py:764-765`）改成只对 `score is not None` 的取均值；若降级数 == 画像总数 → `report["gate"] = "degraded_reader"` 并跳过重写（与 `degraded_review` 同策略）；部分降级 → `report["reader_degraded"] = n` 留痕，仍按有效分判定。

```python
        pipeline.stage_write(cfg, llm, project)
```

对照同一个文件里正确的两处：

```python
            pipeline.stage_write(cfg, llm, project)
            lock.beat("polish")

```

### M1 流式失败一次就把 `stream` 永久关掉，而且是写进进程级共享实例

- **位置**：`studio/llm.py:252-262`（配合 `studio/llm.py:1079-1091`）
- **代码**：

```python
252:                if self.stream:
253:                    try:
254:                        text, usage = self._chat_stream(url, payload)
255:                        self._record(...)
256:                        return text
257:                    except (requests.RequestException, LLMError) as e:
258:                        if attempt >= self.retries + 2:
259:                            raise
260:                        print(f"    [llm] 流式失败（{e}），降级为非流式重试")
261:                        self.stream = False
262:                        continue
```

- **问题**：两个问题叠加。
  1. `self` 来自 `_LLM_CACHE`（`get_llm` 的缓存），**是进程内所有调用共享的那一个实例**。一次读超时 → `self.stream = False` → 此后**整个进程**的所有写作/审稿调用都不再流式，且没有任何恢复点。
  2. 这条 `continue` **跳过了 `time.sleep`**（退避只在 342 行的 except 分支里），所以瞬时网络抖动会变成一次无间隔的紧循环，最多连撞 `retries + 2`（默认 5+2=7）次。
  下游已经有人试图修这件事但修不干净：`pipeline.py:2205-2217` 在"初稿疑似截断"时保存 `stream_backup = writer_llm.stream`、置 False、`finally` 里恢复 —— **因为 M1 已经把 `stream` 置成 False，这里的 `stream_backup` 备份到的就是 False**，恢复等于没恢复。
- **修法**：降级标记放到**单次调用**上，不要改共享状态；并给这条路径补退避：

```python
                    except (requests.RequestException, LLMError) as e:
                        if attempt >= self.retries + 2:
                            raise
                        print(f"    [llm] 流式失败（{e}），本次降级为非流式重试")
                        local_stream = False          # 覆盖本次循环的流式开关
                        time.sleep(min(30, 2 ** attempt * 2))
                        continue
```

`self.stream` 只在显式配置变更时改；确需全局降级时，至少 `print` 一行"本次进程内后续调用已关闭流式"。

### M2 非 429 的 4xx（401/402/403/400）也重试 5 次，纯烧时间

- **位置**：`studio/llm.py:269-281` + `studio/llm.py:315-343`
- **代码**：

```python

271:                    if "response_format" in payload:

276:                        payload.pop("reasoning_effort", None); continue

```

```python

321:                max_attempts = self.retries + (2 if rate_limited else 0)
322:                if attempt >= max_attempts:
```

- **位置**：`studio/util.py:143-156`（消费者 `studio/pipeline.py:2383-2388`）
- **代码**：

```python

150:     def wait(self):
151:         if self.min_interval <= 0:
152:             return
153:         elapsed = time.time() - self._last
154:         if elapsed < self.min_interval:
155:             time.sleep(self.min_interval - elapsed)

```

- **问题**：读 `self._last` → 判 → 睡 → 写 `self._last`，全程无锁。`pipeline.py:2383-2388` 用 `ThreadPoolExecutor` 并行跑章级门禁（`max_parallel` 默认 3，`workers` 可到 3），多个线程共享同一个 `BaseLLM` 实例（`_LLM_CACHE`）也因此共享同一个 `limiter`：两个线程同时读到同一个 `_last`，都判定"不需要等"，实际间隔变成 0。限速器形同虚设 → 触发网关 RPM 限制 → 反问 LLM 层重试 → 撞上 M2 的 4xx 重试逻辑。
- **修法**：

```python
import threading
...
    def __init__(self, min_interval: float = 0.0):
        self.min_interval = min_interval
        self._last = 0.0
        self._lock = threading.Lock()

    def wait(self):
        if self.min_interval <= 0:

        with self._lock:                      # 串行化"算等待 + 更新 _last"

```

### L1 `_ensure_serve` 成功路径不关日志句柄

- **位置**：`studio/llm.py:509-519`
- **代码**：

```python

510:        err = open(os.path.join(log_dir, "opencode_serve_err.log"), "a", encoding="utf-8")
```

### 剩余缺口（明确未做）

1. **写手侧预防**：现在只在"检"上收口，写第 N 节时上下文里只有第 N-1 节全文（`ctx["_prev_text"]`），看不到更早的节，所以"复用第 3 节的一句话"从机制上防不住。下一步应把历史章节的**金句/台词清单**（而非全文）注入写手上下文，从"事后检出"升级为"事前不见"。
